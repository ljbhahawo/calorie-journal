# 可食重量与常用份量

用途：记录I2 / 1.7.0的R20实现方案、数据迁移与T29验收。状态：2026-10-23候选功能、源码、迁移、跨结构回退和桌面流程通过，正在完成正式交付；1.6.0及旧版保持独立。最终状态见[开发进度](progress.md)，阶段安排见[后续功能开发计划](后续功能开发计划.md)。

## 操作与范围

每日录入保留已有“重量、g/kg、每100克大卡”表单，增加“换算可食重量”按钮，打开独立简洁窗口。换算仅生成草稿，确认带入后才更新主表单的克数，保存摄入才产生记录。

- 总重扣除：输入总重，逐项输入壳、皮、骨等名称和扣重，分别选择g/kg；显示总重、扣重合计、最终可食克数和大卡。支持多个扣除项。扣重大于总重或最终可食重量为零时明确拒绝带入。
- 常用份量：针对一个具体食物维护“一勺/一份/一个”等名称与用户指定的每份克数，输入份数后计算可食克数。程序不猜测大小、容积或密度。只有关联到当前有效食物才能创建或选择该食物的份量。
- 份量维护有明确新增、保存和删除确认；修改或删除定义不重算历史。编辑或复制历史摄入时沿用当时的计算依据，不能悄悄套用现有份量的新数值。
- 换算窗口取消不改变摄入草稿；已经明确保存的份量定义保持保存。手动修改主表单重量或单位时取消此前换算依据并提示，保存为普通重量计算；仅改变本次单位热量可继续保留重量依据。

## 计算与数据

Core集中计算和校验。重量沿用克×10的整数及decimal，用户输入换算后最多0.1g；份数最多3位小数，最终克数四舍五入到0.1g，再调用既有热量公式，热量仍为大卡×10。边界为最终重量0.1–100000g，单位热量0–10000kcal/100g；负数、精度过多、无效单位、空名称、无效份数及溢出在输入边界拒绝。

增加`FoodPortion`（ID、食物ID、名称、每份克数、删除标记与创建/更新时间）。摄入增加可选`WeightCalculationSnapshot`，保存总重和每项扣重，或份量名称、每份克数、份数与定义ID；保存时重新验证结果等于既有最终重量字段。旧条目不添加推测依据，继续显示原计算方式。

SQLite升级为结构2，新增份量表及摄入依据列；依据为使用标准System.Text.Json编码的结构化JSON，读取时严格验证，不手写解析。完整备份升级为格式2，包含份量与计算快照；允许明确导入格式1/结构1备份并补空份量，校验不兼容版本、重复ID、非法引用及计算不一致。格式1不能夹带新字段或份量数据以逃避版本要求。

迁移前使用SQLite在线备份生成独立结构1数据库，并执行完整性检查及版本检查，记录来源版本和校验值；备份失败终止升级，事务迁移失败保留原结构。旧版1.6看到结构2须拒绝写入。初始化、读回、备份与恢复不丢失用户修改和删除标记。

## 回滚与交付

1.7不得声称与1.6数据结构直接兼容。升级前保留1.6导出的完整格式1备份。回退先由1.7导出完整当前格式2归档，再由1.6在独立暂存目录校验恢复所选旧备份，核对成功后原子替换工作数据库并保留被替换的数据库；沿用版本指针和实例锁保护。

回退说明必须显示备份时间点，明确后来新增的摄入、份量和计算依据暂时不在旧版工作视图中，但完整保存在新版归档。返回1.7后可通过恢复该归档取回全部数据。失败时保持现有数据及指针可追踪，不删除旧程序包或归档，不用Git撤销历史。

## T29验收与顺序

1. 真实Core/SQLite检查g/kg、多个扣除项、0.1g与3位份数精度、舍入、零/负数、扣重超限和错误单位；数据库中热量与显示一致。
2. 份量增改删、同名约束、食物不存在/删除、重启回读、历史编辑及复制快照；份量改值和删除不能改写已保存条目。
3. 使用实际1.6程序生成明确的测试记录、食物修改/删除和格式1备份，升级至结构2，核对逐项历史不变、升级前数据库备份可被1.6读取、迁移失败保护。旧程序对结构2写入失败且文件不变。
4. 格式2完整备份恢复包含份量与依据；格式1恢复明确空份量；非法和不完整备份不能部分写入，恢复前先归档现有数据。
5. 真实WPF及实际桌面完成换算、份量维护、带入不保存/明确保存、历史回读；最小窗口及四档布局缩放可达，取消保留原草稿。
6. 完成全部核心回归、源码独立锁定重建、自包含程序和包校验；在隔离目录实际执行1.7→1.6旧恢复点→1.7并恢复新归档，逐项比较食物、餐次、摄入、份量及计算快照。通过后才创建稳定标签和公开Release。

实施顺序：计算与数据模型 → 迁移/持久化/完整备份 → 真实数据保护检查 → 换算与份量窗口 → 主表单及历史连接 → 全部验收与交付。普通界面和命名决定由开发助手记录；不新增付费资源或网络用途。

## A01：清空按钮的重复操作验收失败

- **状态/优先级：** 已确认测试失败，P1；尚未确认普通鼠标操作的全部触发条件。
- **表现与证据：** 本轮隔离运行在 [SheetBindingChecks.cs](../../tests/CalorieJournal.Desktop.Tests/SheetBindingChecks.cs) 第31行重复失败。第一次清空及绑定更新、撤销后的文字恢复已经执行；第二次 `IInvokeProvider.Invoke` 抛出 `ElementNotEnabledException`。
- **相关实现：** [TextInputCommands.cs](../../src/CalorieJournal.Desktop/TextInputCommands.cs) 第12–14行，`CanExecute` 包含文本非空判断；[SharedStyles.xaml](../../src/CalorieJournal.Desktop/SharedStyles.xaml) 第56、64–66行同时按文本/只读/禁用设置显示状态。
- **根因判断：** 命令可用性重新查询与 Undo 后模板状态更新时序是候选原因；测试的 Dispatcher 等待方式也需核对，不能直接认定框架问题或仅延长等待掩盖故障。
- **影响：** 共享样式影响所有采用该样式的文本框；且失败使后续表格功能尚无执行证据。
- **方案：** 先用真实鼠标和键盘复现，记录文本、绑定、可用性状态。再选择最小修复，明确“显示条件”和“命令可执行条件”各自职责。禁止在测试中强制设置按钮 Enabled 或绕过真实命令。
- **验收：** 清空、Undo、Redo、重复清空、粘贴、中文输入完成后的清空、空/只读/禁用、草稿与搜索刷新均正确；旧表单与表格都覆盖。
- **成本/风险：** 0.5–2人日；共享控件修复范围广，需完整相关 UI 回归。

## A02：发布元数据与迁移验证没有同步

- **状态/优先级：** 已确认，P1，仅针对未完成 1.13 工作区；不能据此否定 1.12 的既有清单。
- **表现与位置：** [SqliteJournalStore.cs](../../src/CalorieJournal.Infrastructure/SqliteJournalStore.cs) 第12–13行是 8/8；[Publish-Release.ps1](../../scripts/Publish-Release.ps1) 第76行仍生成 7/7。[Verify-DataMigration.ps1](../../scripts/Verify-DataMigration.ps1) 第11、74行已接受旧结构7并要求新结构8，而 [MigrationChecks.cs](../../tests/CalorieJournal.Desktop.Tests/MigrationChecks.cs) 第19行只接受1–6，第57–58行仍假定营养列不存在。
- **根因：** 数据版本和旧结构能力在多个脚本及断言中手动维护；目前处于未收尾的开发状态。
- **影响：** 当前打包会写错误版本信息；7→8迁移验证无法按计划完成。尚未证明生产迁移本身错误。
- **方案：** 由程序输出可校验的版本能力信息，打包与验证读取同一依据；迁移断言按实际旧版本检查列和数据。增加拒绝“清单/程序/导出版本不同”的发布检查。
- **验收：** 源码、程序、manifest、导出备份一致；实际旧程序产生的1–7结构全部完成升级验证，8→7→8逐项保留九类集合、设置及营养快照；故意不匹配清单必须被拒绝。
- **成本/风险：** 1–3人日；改动集中在验证与打包，但影响发布资格，旧版归档必须保持原样。

## A03：完整备份读写容量不一致

- **状态/优先级：** 已确认静态代码缺陷，P1；本轮没有构造大型数据库或执行超限恢复。
- **证据：** [JsonFiles.cs](../../src/CalorieJournal.Infrastructure/JsonFiles.cs) 第18行拒绝大于52,428,800字节的文件；第23–43行写出没有同等限制或回读。[BackupService.cs](../../src/CalorieJournal.Infrastructure/BackupService.cs) 第14–35行导出/恢复前归档直接调用写出，并不核验该文件能由 `Inspect` 读回。这两个文件相对 `v1.12.0` 无差异。
- **可验证反例：** 当前校验允许单条3000字符来源和1000字符备注，允许最多10万摄入；14000条合法条目仅这两个 ASCII 字段就超过5600万字节，尚未计入其他字段和 JSON。数量校验通过不保证文件可读。
- **根因：** 防止大文件读取的保护没有与应用允许产生的数据规模共同设计。
- **影响：** 可能导出“成功”但本应用拒绝恢复的备份。恢复前归档也可能不可读；而升级前流程会回读并停止，故升级路径表现为阻塞，不能把两者混同为都已丢数据。
- **方案：** 定义统一容量策略，保证允许保存的数据可导出并恢复。对写出的暂存备份做真实回读/结构校验后再宣告成功或替换工作数据。若调整读取上限，需保留大小、深度、数量与内存保护，不无条件取消限制。既有超限库须有保全方案，不能要求删除记录才能备份。
- **验收：** 正常、接近上限、超50MB、长中文/ASCII、写入占用/失败场景；新备份读回并逐项比较；前置备份不可读时恢复不替换原库。规模输入明确是测试数据，真实 SQLite/JSON 全程使用，不用 mock。
- **成本/风险：** 2–4人日；数据保护优先，主要风险是内存峰值、文件大小策略和旧版兼容。

## A04：不同写入入口对数据总量的约束不一致

- **状态/优先级：** 已确认静态路径不一致，P1；触发通常需要长期使用或大量录入，实际影响频率未测。
- **证据：** [Validation.cs](../../src/CalorieJournal.Core/Validation.cs) 第107行限制食物/摄入各10万、餐次1000。[JournalService.cs](../../src/CalorieJournal.Core/JournalService.cs) 第76–98行及 [SqliteJournalStore.cs](../../src/CalorieJournal.Infrastructure/SqliteJournalStore.cs) 第241–243行的普通保存无总量校验。文字导入、模板、目标及锻炼则有部分数量保护；`SaveEntryAndFood` 检查新增食物数但不检查摄入总数。
- **根因：** 上限在备份和逐版新增功能中分散添加，没有统一“保存后仍可完整备份”的约束。
- **影响：** 合法的单条保存可把数据库推到完整备份拒绝的状态；恢复前备份或升级也可能被阻塞。未观察到真实用户达到该状态。
- **方案：** 在实际写事务中统一新增数量判断，编辑已有 ID 不应因达到上限而受阻；同时明确删除标记是否计入总量。与 A03 共同设计超限已有库的可恢复处理，不只阻止未来新增。
- **验收：** 所有手动、表格、入库联写、导入、模板入口在边界前后行为一致；编辑、删除、失败回退及备份仍可用；事务失败不部分新增。
- **成本/风险：** 1–2人日，可与A03共享准备；须防止把“编辑”误判为“新增”。

## A05：WPF 测试依赖前序目录与时间

- **状态/优先级：** 已确认工程问题，P2；当前交付先用严格独立的运行目录隔离风险。
- **证据：** [SheetBindingChecks.cs](../../tests/CalorieJournal.Desktop.Tests/SheetBindingChecks.cs) 第23行、`NutritionBindingChecks`/`PersonalBindingChecks`第22行及`StatisticsBindingChecks`第22–23行选择最近修改的 `wpf_*` 目录。[BindingCheckProgram.cs](../../tests/CalorieJournal.Desktop.Tests/BindingCheckProgram.cs) 固定串行执行；[Test-Project.ps1](../../scripts/Test-Project.ps1) 第9行使用共享 `workspace/tests`，第27行对整套 WPF 固定30秒。
- **根因/影响：** 复用前版测试库逐步积累覆盖；单测难独立重跑，共享目录并行时可能取到别次产物。现有顺序运行并不因此自动无效，但单个通过标志不能证明后续检查执行。
- **方案：** 每次运行唯一目录与运行标识，显式传递本次真实 fixture；逐功能输出执行/通过/失败/未执行。按功能拆分可选检查入口与合理超时；保留整体回归入口。
- **验收：** 单独运行新增功能不依赖旧残留目录；两次独立运行不互相取文件；中途失败后报告明确列出未执行项。禁止通过复制旧“成功报告”补齐结果。
- **成本/风险：** 1–3人日；不能在整理时失去原始失败覆盖或改写历史证据。

## A06：表格和名称联想的性能风险

- **状态/优先级：** 高可信度潜在问题，P2；未测得用户可感知卡顿，不能宣称性能目标已失败。
- **证据：** [MainViewModel.Sheet.cs](../../src/CalorieJournal.Desktop/MainViewModel.Sheet.cs) `RefreshSheet/CreateSheetRow` 为区间每条记录构造模型；[SheetEntryViewModel.cs](../../src/CalorieJournal.Desktop/SheetEntryViewModel.cs) `Load` 再调用 `journal.Meals()`。`Suggest` 的 `Take(12)` 位于 [JournalService.Foods](../../src/CalorieJournal.Core/JournalService.cs) 完整读库、构造检索文档和排序之后；[FoodNameInput.xaml.cs](../../src/CalorieJournal.Desktop/FoodNameInput.xaml.cs) 在文本变化时同步调用。
- **根因/影响：** 从小规模表单扩展为连续编辑表格时沿用逐次数据库读取。外层虚拟化只约束视觉对象，不消除行模型和查询成本；多条草稿也增加刷新遍历。
- **方案：** 先测量冷/热查询、构造数量、连接次数、耗时和内存，再决定一次读取餐次上下文、按资料版本缓存检索文档、输入合并或异步查询。异步结果必须校验查询版本，避免旧候选覆盖新输入。
- **验收：** 60项与完整公开目录规模的个人库、30/366天、1千/1万及支持上限记录量分别测量；以需求中的普通查询/搜索300ms作为目标，记录环境、样本与p50/p95，未达标明确限制；刷新不丢草稿和来源快照。
- **成本/风险：** 测量0.5–1人日，确需优化再1–3人日；缓存失效和跨线程绑定是主要风险。

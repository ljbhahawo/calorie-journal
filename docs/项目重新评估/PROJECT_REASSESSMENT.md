## 1. 结论

项目已经具备实际个人记账软件的主体能力，具有可运行的稳定归档、真实 SQLite 测试和较完整的数据回退机制。**建议保留 C# / WPF / .NET / SQLite 的总体结构，以数据保护修复、当前功能验收和局部重构继续完善。没有发现足以支持整体重写的证据。**

当前主要矛盾是：功能增加很快，录入状态、数据版本、发布脚本及验证证据的维护已经需要人工在多处同步。测试数量增加，并没有自动解决大数据备份边界、表格交互和干净环境交付的缺口。

优先级应从“依次增加功能”调整为“保证能安全保存和恢复 → 完成当前表格功能 → 稳定可重复的验证与发布 → 自动备份 → 有证据支持的局部改善与新功能”。

## 3. 产品目标与真实实现

目标仍是 Windows 11 单人离线饮食记录：快速输入、可靠保存、按餐/按日理解摄入，并能迁移和恢复个人资料。身体记录与运动是辅助功能，不应改变摄入的原始含义。没有账户、云同步或跨平台需求证据。

| 功能 | 状态 | 交叉核对与限制 |
|---|---|---|
| 摄入增删改、日期/餐次、直接或重量录入 | 已实现并有稳定版证据 | `JournalService`、`MainViewModel`、业务及真实 WPF 检查；当前新增共享控件仍可能影响旧表单 |
| 大卡/kJ、蛋白质、可食重量、份量、历史快照 | 已实现并有稳定版证据 | `Nutrition`、`WeightCalculator`、`IntakeEntry`、营养/份量测试；缺失蛋白质与零分别保存 |
| 个人食物库及参考目录 | 已实现 | 60 项起始库，USDA 7793、TFDA 2213 的参考资料；个人库与参考目录是两个不同对象，参考结果需明确加入个人库 |
| 中文/别名搜索及来源追踪 | 已实现；语义覆盖不能视为全面证明 | 共用 `FoodSearch`、独立中文索引与哈希验证；140 条查询回归不证明全部 7793 条中文描述都无误 |
| 文字/复制表格导入 | 已实现 | `IntakeTextParser`、`ImportPlanner`、独立预览及事务追加；歧义需要人工核对；不支持直接读取 Excel、图片、PDF |
| 餐食模板 | 已实现 | 食物、份量引用及批次幂等；模板带入会检查当前引用，已存摄入保持快照；不是成品重量菜谱计算 |
| 周/月统计和趋势 | 已实现 | `IntakeStatistics` 明确按条目数区分缺失与零；平均值只覆盖记录日，不能解释为完整饮食平均 |

## 4. 架构与工程判断

三个生产项目的依赖方向基本合理：Desktop 组装 Core 服务与 Infrastructure 实现；Core 保存计算、模型与业务验证；Infrastructure 负责 SQLite、JSON 与公开目录。两个测试项目分别承担业务/SQLite 和独立 STA/WPF 检查。生产依赖较少，版本与五个锁文件明确，SDK 固定为 10.0.402。

值得保留：

- `decimal` 与缩放整数、原始 kJ 和营养快照，避免食物更新重算历史。
- SQLite 参数化 SQL、外键、事务，一致性快照读取和恢复前归档。
- 用户主动联网更新公开资料、下载和解压上限、取消处理及缓存替换；日常摄入不依赖远程服务。
- 不推断缺失热量、蛋白质、完整记账日或未知份量；运动与摄入独立。
- 不覆盖稳定包的版本归档与独立源码重建思路。

应局部改善：

- `MainViewModel` 虽分成多个 partial 文件，仍共享大量草稿、刷新和导航状态；文件拆分没有形成独立职责边界。
- 经典录入与 `SheetEntryViewModel` 已重复实现单位文本换算、输入组装、来源调整及草稿处理。核心公式已共用，应只抽取真正重复的编辑规则，不引入通用表单框架。
- 表格每条记录构造时读取餐次；名称每次变化读取并重建整个个人库的搜索文档。界面虚拟化不会消除这些数据读取和模型构造成本。
- 数据库与备份版本被要求相等，页面偏好也放入同一严格格式。当前 8 版本可避免旧版悄悄丢字段，但为纯界面设置增加了升级/降级成本。需要先明确兼容策略，不能直接删去保护。

## 7. 三种总体策略比较

| 策略 | 收益 | 成本与风险 | 对现有功能的影响 |
|---|---|---|---|
| 保留架构，只逐项修补 | 最快处理 A01–A04，便于控制差异 | 后续两种录入界面继续重复修正；验证脚本仍容易不同步 | 短期风险小，长期维护成本继续增加 |
| **保留总体架构，局部重构关键路径** | 修复数据边界，同时统一编辑规则、导航标识和验收元数据 | 需要先建立行为回归；每次只移动一项职责 | 推荐；旧页面和数据库语义可持续保留，逐版本验证和回退 |
| 较大范围架构调整/重写 | 只有新增跨平台、多人同步等目标时才可能明显受益 | 重做绑定、迁移、打包及既有交互，成本最高；目前无相应需求 | 容易丢失已有边界处理和验收积累，本轮不推荐 |

推荐方案的核心是先证明行为，再调整代码边界；不采用微服务、云后端、事件总线或通用插件系统作为本项目的前置工作。新路线图不承诺实现日期或未知可用额度，完成标准以可复查的验收结果为准。

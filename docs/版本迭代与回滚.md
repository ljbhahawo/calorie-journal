# 版本迭代与回滚

用途：规定首版完成后的自主改进范围、稳定版本保留及程序和数据回退方式。依据：用户2026-10-22明确授权自主改进并要求每版可回滚，2026-10-23接受后续功能并新增图标、USDA中文及别名搜索。当前1.5.0稳定版与全部旧版已保留，实际版本状态见[开发进度](progress.md)。

## 1. 进入条件和迭代顺序

先完成 [需求说明](requirements.md) 中首版全部功能和 [测试与验收](测试与验收.md) 的首版检查，保存可实际运行的1.0.0稳定基准；不得为了新功能推迟核心交付。

北京时间02:10和07:11两次续办都适用：首版已完成且仍有实际可用额度，就按下列优先级自主选择改进，持续执行并记录。已有明确授权的普通选择无需等待用户；不另建未要求的自动唤醒。

1. 修复实际发现的计算、数据保护、操作流程、启动或性能问题；完善测试覆盖、错误提示、键盘操作和使用说明。
2. 根据当前软件和剩余额度选择一个相关小功能，先明确该版范围与验收，再实现和验证。
3. 核心回归、备份兼容及实际回滚演练通过后，保存新稳定版；若仍有额度且有明确价值，继续下一个小版本。

修复使用补丁版本，如1.0.1；新增兼容功能使用次版本，如1.1.0。示例版本号不代表必须按指定次数发布。每个版本都记录范围、原因、数据结构影响、实际验证与回滚目标。

## 2. 已授权候选功能及通过标准

下表为可选择的后续范围，不要求在首版或一次运行中全部完成。具体版本确定后，在开发进度中说明选择及原因；若需要更详细规则，先补充设计后实现。

| 方向 | 简洁的候选范围 | 选用该方向后的必要验收 |
|---|---|---|
| 锻炼记录 | 按日记录活动名称、时长、备注，可选用户输入的消耗大卡；可增删改查 | 零/负时长和无效输入处理明确，修改及重启后正确；摄入与运动分别展示，运动消耗不能隐式抵扣摄入合计 |
| 菜谱 | 用户维护菜谱、食材重量、制作说明和份数；从食物库引用并计算整份及每份热量，可按份添加摄入 | 食材逐项可追溯，份数必须有效；食物或菜谱后续改动不重算历史摄入；整份/每份及实际加入记录的舍入规则一致 |
| 减脂过程记录 | 用户手动记录体重、设置个人摄入目标，查看简单日期列表或趋势及已记录摄入与目标的差值 | 未记录与零值区分；目标有生效日期，之后修改不改写历史目标；不根据缺少的身体信息推算处方或承诺减重结果 |
| 日常录入便利 | 常用条目、最近使用、复制指定餐次或数据检索改进，依据实际交互选择 | 用户主动确认产生的新记录，复制后可编辑；防止重复提交；保留来源快照；原有录入流程可用 |

界面保持中文、信息清楚，沿用现有页面组织和样式；不为了展示加入复杂动画、社交功能或大型仪表盘。食材数据来源沿用食物库审核规则；新增数据类型进入完整备份并具备恢复验证。

2026-10-23上述部分候选已由用户接受为后续开发范围，并补充可食重量与份量、餐食模板、周/月统计、自动备份导出、应用图标和USDA中文/常用别名搜索。当前选择顺序、需求及验收以[后续功能开发计划](后续功能开发计划.md)为准；先完成中文搜索与图标。既有稳定版及回滚规则继续适用，新数据类型必须纳入完整归档，不能仅验证旧摄入记录而遗漏模板、身体测量或菜谱。

## 3. 版本保留

每个通过验收的版本独立保存到`artifacts/releases/<version>/`，不覆盖现有稳定版本。计划产物如下，具体文件仅在实际生成后登记为存在：

| 产物 | 内容 |
|---|---|
| 程序压缩包及可运行目录 | 对应版本的Windows x64程序及依赖 |
| 源码快照 | 该版源码、构建脚本、依赖锁文件、迁移及必要数据包；排除工具缓存、用户数据和凭据 |
| 版本与校验清单 | 应用版本、SDK与依赖版本、数据库/备份/食物包版本、SHA256及实际构建信息 |
| 变更与兼容说明 | 新增/修复内容、验证结果、已知限制、可回到的上一稳定版及其数据兼容条件 |
| 回滚入口与使用说明 | 本地可重复操作入口、预检查、目标版本、备份选择和失败处理 |

用户数据备份保存在用户数据目录或用户指定位置，开发验证备份保存在项目隔离测试目录；真实用户数据不进入程序包或源码快照。可分享文件的校验清单不包含私人数据内容。

用户于2026-10-22长期授权本项目在每次更新完成并通过相应验证后自动提交、推送GitHub。稳定版本须完成本文件规定的验收及回滚演练，再创建并推送`vX.Y.Z`附注标签并保留完整Release。已有标签、Release、程序包、源码和数据恢复路径持续保留，不覆盖旧版；普通文档修改仅提交和推送，不单独增加软件稳定版本。具体操作见[Git管理说明](Git管理说明.md)。

## 4. 升级和程序回滚

升级前退出写入实例，核对目标版本与必要磁盘空间，用SQLite备份机制或已验证的一致性导出生成数据恢复点并验证可读。备份失败停止升级。新版本使用独立程序目录，迁移提交后才标记升级成功；失败保留上一程序和原数据。

返回旧版前读取版本清单，确认程序包校验、目标数据库版本及完整备份是否可用，不通过则停止并说明原因。首选与上一稳定版兼容的结构变化；确需不同结构时提供明确恢复过程。

| 情况 | 回滚操作 | 数据影响 |
|---|---|---|
| 两版程序验证为兼容当前数据 | 备份当前数据后，切换到上一版独立程序目录并实际启动、查询 | 当前记录保留；旧版未提供的新功能可能不可操作，不能写坏新增数据 |
| 旧版无法读取当前数据 | 先完整归档当前新版数据库和元数据，确认归档可读；预览并确认旧恢复点；通过安全恢复入口恢复旧版可读数据，再切换程序 | 旧版工作视图回到备份时间点；升级后新增记录仍留在新版归档，清楚说明旧版无法显示的范围 |

不能把应用版本号较小视为数据必然兼容；未经过检查的旧版禁止对新版数据库写入。恢复旧备份是会改变当前工作视图的操作，入口需要明确说明时间点和影响并由操作者确认，不能因已有迭代授权而静默替换真实用户数据。

回滚过程先完成数据与文件校验，再执行切换或安全替换；失败时保留两版程序与新旧数据，不删除当前归档。重新启用新版时可以恢复刚才保存的新版数据归档，后续如何处理回滚期间新增的记录须清楚说明，首版不做未经验证的自动跨版合并。

源码回退依靠版本快照及受审查的文件编辑，可通过Git标签查看版本或导出到独立目录，不使用Git恢复、清理或历史重写命令覆盖工作。项目已纳入Git管理；应用及数据回滚继续使用完整版本包和安全恢复入口。

## 5. 实际演练和稳定标准

1. 1.0.0保存稳定基准，验证归档解压、启动、数据库和备份可读；没有更早正式版，不声称已经做了跨版回滚。
2. 每个后续版本使用独立测试目录，从上一稳定版创建并保存测试记录，再运行新版升级。
3. 在新版执行该版新增功能，验证修改、重启、完整备份恢复，并执行核心回归。
4. 按实际兼容路径返回上一稳定版，检查可启动、可查询和应保留的数据；若恢复旧备份，检查新版新增数据归档仍完整存在，且界面/入口明确展示恢复点及影响。
5. 恢复归档并重新启用新版，验证新版记录可回读。缺失包、损坏备份、版本不兼容、备份失败和存在写入实例时应安全停止。
6. 保存实际操作、测试结果和兼容矩阵后才能标记新稳定版。只保留旧程序或只提供恢复说明，均不等于完成回滚验收。

## 6. 运行结束和接续

实际额度或时间上限临近时，优先完成正在执行的安全写入、保存修改和更新进度。未完成新功能标记为开发中，记录未通过检查和下一步，保留最后稳定版供使用；不将部分实现标为稳定交付。

用户可从开发进度查看版本清单、每次自主选择的原因、已完成与未完成内容、验证结果和实际回滚范围。当前rc.2→rc.1→rc.2已在独立目录真实执行并保留3条测试记录；显式恢复旧快照后，新版数据归档亦可重新恢复。报告位于`artifacts/test-results/cross-candidate-rollback.json`，实际数据库结构均为1。未来结构变化必须补充对应迁移与跨结构回退验证，不能沿用本次结果冒充完成。

# 运行与验证

用途：提供开发者可以重复执行的构建、测试和本地打包步骤。所有示例工作目录为`E:\codex\calorie-journal`，使用PowerShell 7；只更改当前进程环境及本项目文件，不修改全局配置。普通用户运行方法见 [使用说明](使用说明.md)。

## 工程结构

生产代码位于`src/CalorieJournal.Core`、`src/CalorieJournal.Infrastructure`、`src/CalorieJournal.Desktop`，分别承担规则与接口、SQLite及文件存储、WPF界面。测试位于`tests/CalorieJournal.Tests`及`tests/CalorieJournal.Desktop.Tests`；后者是带真实应用消息循环的独立STA检查程序。

食物选择和中文映射在`data/food-selections.json`，生成的食物包与逐项来源在`data/builtin/`。`scripts/`管理项目环境、生成数据、测试、打包和发布验证；`workspace/`与`artifacts/`包含忽略管理的中间文件及产物。

## 环境与构建

```powershell
Set-Location E:\codex\calorie-journal
.\scripts\Initialize-Environment.ps1
.\scripts\dotnet.ps1 restore .\CalorieJournal.slnx --locked-mode
.\scripts\dotnet.ps1 build .\CalorieJournal.slnx --no-restore '-m:1' '-p:UseSharedCompilation=false'
```

首次准备SDK及还原NuGet依赖需要网络。SDK固定10.0.402，下载后核对官方SHA512；`global.json`固定版本，包版本由各项目及`packages.lock.json`记录。后续升级依赖应更新并复核锁文件，不静默改动全局SDK或其他项目环境。

1.1.1起，`Directory.Build.props`统一声明`RuntimeIdentifiers=win-x64`；普通还原与自包含发布共用五个锁文件。日常构建和发布使用锁定还原，不能用删除锁文件或关闭锁定来跳过不一致。确实修改依赖或目标时，由维护者明确重新生成锁文件并审查版本与内容哈希。

该设置依据微软的[RID说明](https://learn.microsoft.com/en-us/dotnet/core/rid-catalog)和[发布命令说明](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-publish)：运行时目标可在项目声明；发布默认会隐式还原，可用`--no-restore`关闭。实际行为同时在项目固定SDK中验证。

当前环境的沙箱限制测试宿主的进程通信，首次VSTest连接超时；在环境审批允许本地进程通信后，同一真实测试正常运行。不能通过增加超时将通信受限冒充测试通过。

## 食物包重新生成

将官方`FoodData_Central_sr_legacy_food_csv_2018-04.zip`解压到`workspace/usda-sr/`，保留与下载档案一致的子目录名；压缩包本体置于`workspace/downloads/`。使用Python 3标准库即可生成：

```powershell
py -3 .\scripts\prepare_foods.py
```

脚本逐项核对原名、稳定ID、能量字段、单位、精度、范围和重复条目，再生成60项数据与来源清单；不依赖全局科研Conda环境。当前机器实际使用`C:\Python313\python.exe`完成该步骤。重新生成会更新来源清单的实际生成时间，食物ID及原始数值不改变。

蛋白质补充使用同一USDA原档及TFDA原档，运行`py -3 ./scripts/prepare_protein.py`，核对原始档案和现有目录SHA256、USDA营养素1003/Protein/G及TFDA粗蛋白/g后生成`data/lookup/protein.json`。版本`protein-2026-10-23.1`，USDA 7793有值，TFDA 2183有值/30缺失。原热量目录与中文索引不改写；运行时校验补充文件哈希及来源版本后关联。

## 独立源码重建

`Verify-Source.ps1 -ReleaseVersion <版本>`先校验包内`source.zip`，解压到全新`workspace/source_check_<版本>_<编号>/source`，使用固定SDK与项目缓存，执行：普通锁定还原→构建→归档内全部真实业务/SQLite测试（1.4为26项）→真实WPF检查→发布锁定还原→自包含发布→普通锁定还原与构建→实际启动重建程序。全过程不能修改五个锁文件。它使用新生成的构建输出，不使用主目录的bin/obj；包缓存仍复用，未声称为空缓存或另一台干净机器验证。

成功或失败均写入`artifacts/test-results/source_<版本>_<编号>.json`，详细命令输出、TRX与测试数据库位于报告指定的独立目录。1.0.0与1.1.0旧源码归档没有统一RID，原有默认锁定还原存在NU1004；旧归档保持原样，后续开发使用1.1.1及更新源码。

1.5设置`IncludeSourceRevisionInInformationalVersion=false`，使产品版本严格使用声明版本，不因归档解压在外层Git仓库下而附加无关父仓库提交号。Git追溯使用版本标签、源码ZIP及校验值；[微软属性说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/set-attributes-project-file)说明了SDK的默认追加行为。

验证脚本在带中文和空格的独立目录解压，核对全部清单，令外部DOTNET_ROOT指向不存在位置，实际运行图形程序与维护命令，检查启动、完整备份恢复、非法备份拒绝及兼容回滚入口。报告写入`artifacts/test-results/release_<version>.json`。两版之间的往返回滚另行记录，不将同版本入口检查当成跨版本演练。

回滚验证脚本接受`-OldVersion`与`-NewVersion`，并可通过`-FixtureDatabase`指定`workspace/tests`内已关闭的真实测试数据库；默认使用两条明确输入的SQLite集成检查库。1.1验收使用包含复制和编辑结果的WPF测试库，逐条比较完整摄入快照，不能只比较数量。报告为`cross-rollback_<new>_to_<old>.json`；原rc.2→rc.1报告保留为`cross-candidate-rollback.json`。实际结构均为1，不代表未来数据结构都可直接回退。

稳定版本要求必要回归、独立源码重建及候选包检查完成，再显式使用`Publish-Release.ps1 -ReleaseVersion 1.3.0 -Stability stable`生成新目录，随后复验正式包的源码、发布程序和往返回滚。脚本默认candidate，不自动把构建成功标为稳定；版本目录不允许覆盖。涉及界面变化时还须补充实际桌面操作；首版没有更早正式版，其后版本须对实际上一稳定版执行往返。
